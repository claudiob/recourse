Routes

Everything a routes line can say. recourses works anywhere resources does and takes the same options; what follows is what it does with them, and the two keywords it adds.

recourses

recourses :users
recourses :posts, only: %i[index show]
recourses :drafts, except: :destroy

Each line draws the routes resources would draw, records the resource in the order it was declared — which is the order of the sidebar — and defines a controller where the host has none. The controller is made on the app’s first request rather than while the routes draw, so a production db:migrate, which draws its routes before the app is done booting, loads nothing early.

What each routed action earns is in Getting started. Two are worth repeating here because they read differently in the routes file: create without new gets a one-click Create button, and destroy without edit gets a Delete on each row of the table.

Nesting

recourses :posts do
  recourses :comments
end

A block nests what it declares under each record, at /posts/5/comments, and namespaces the nested controller after the parent: Posts::CommentsController stays a second controller beside the top-level CommentsController, with templates of its own under app/views/posts/comments/.

A nested resource defaults to only: %i[index new create] — the parent’s rows, and a form to add one under it. An explicit only: or except: is the host’s word and wins. The rows a nested index lists are the parent’s: the gem narrows the model by the foreign key that names the parent, and a form under the record already has that key set.

What a nesting earns on the parent’s card depends only on what it routes. An index earns a tab, reading 8 comments where the parent keeps a counter cache and the bare Comments where it does not. A create with no index earns a button beside the breadcrumb instead — Add note — and a write with no page of its own to land on goes back to the record the button stood on. A parent need not have an association of the nested name at all: the tab is then named after the route, and the rows are the host’s to narrow with recourse_relation; see Customizing.

Nesting inside a plain resources block is refused, because it adds no namespace and every nested page relies on one. Nest under recourses instead.

Namespaces and modules

scope module: :admin do
  recourses :products
end

namespace :admin do
  recourses :products
end

Both put the controller under Admin::. The first keeps the path at /products, the second moves it to /admin/products. A model named with a namespace lists the model the last segment names: admin/products is a Product.

A namespace may sit between a block and what it nests:

recourses :users do
  namespace(:quick) { recourses :notes, only: :create }
end

The routes and the controller come out under it — Users::Quick::NotesController — and a page filed there earns no tab, being reached from nowhere. A bare action filed there still earns its button.

Singular resources

recourses :users do
  recourse :profile, only: %i[new create show]
end

recourse draws what Rails’ resource draws: one record reached with no id of its own, at /users/5/profile. Rails routes a singular resource to a plural controller, so Users::ProfilesController answers it, and the gem reads the record off the parent under the name the route gives — user.profile, whether the parent keeps it with a has_one or points at one with a belongs_to. Where the parent has no association of that name the record is still the host’s to find, with a find_resource of its own.

A singular resource holds at most one, and the two directions follow from that. Routed show, it earns a tab on the parent’s card reading the model’s own word in the singular. Where the record is missing and new is routed, show sends the reader to the form; where it is present, new sends them to the page that reads it. A write has no index to return to, so it lands on the record’s own page.

Routed create or destroy and neither index nor new, a singular resource is a button beside the breadcrumb — Add badge, Delete badge — and which of the two it offers is the record’s to say: nothing to add where there is already one, nothing to delete where there is none.

Bare actions

recourses :posts do
  recourse :publication, only: :create
end

A name this app has no class for is a verb, and the gem still draws its button on the parent’s pages, labelled from the path alone: Add publication. The host writes the controller, a RecoursesController like every other screen:

class Posts::PublicationsController < RecoursesController
  def create
    post = Post.find params.expect(:post_id)
    post.publish!
    flash.notice = "Published #{post.title}"
    redirect_to post_path(post), status: :see_other
  end
end

A rejection with no form to send it back to goes back to the page the button stood on, with what turned the write down as the message.

The two keywords

recourses :tasks, positionable: true
recourses :orders, only: :index, retrievable: true

positionable: true draws the route a dragged row reports its place to, under the index. The column decides everything else; see Positionable tables.

retrievable: true draws POST /orders/retrieval — under the parent, where the resource is nested — and puts the Retrieve button on the table. The controller is the host’s to write; see Retrievable tables.

Both are refused on a resource with no index: a row is dragged from the table that lists it, and the button that fetches rows again stands on that same table, so without one there is nowhere for either to be.

The exit route

resource :session, only: :destroy, as: :exit

A route named exit gives the foot of the sidebar a log-out button beside the light/dark toggle. The route is the whole declaration; the controller is the host’s. The button is submitted by the browser rather than by Turbo, since a log out usually ends with a redirect to another origin.

What is refused

Each of these raises Recourse::Error while the routes draw, with a message naming the line to fix:

  • A recourses name with no model behind it.
  • A recourses nested inside a plain resources block.
  • positionable: true or retrievable: true on a resource that draws no index.

Two more are raised when a page draws rather than when the routes do, since both need the model loaded: a filter in filter_fields Ransack will not answer, and a positioned model pointing several ways without a recourse_siblings. Both are in Models.
