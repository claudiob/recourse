Getting started

This guide installs the gem, routes one resource, and walks through what that one line draws. After it you will know which screens a routed action earns, where the sidebar comes from, and how to put a guard above every screen at once.

Installing the gem

# Gemfile
gem 'recourse'

Nothing else goes in the host. The pages need Turbo, which turbo-rails brings as a dependency, and everything a page is styled and scripted by — Bootstrap, its icons, Turbo, Stimulus and the controllers behind these screens — is bh, which this gem depends on and whose engine serves them at /bh/. A host without an asset pipeline gets the same screens, and nothing is fetched across a network. A host serving those files from somewhere else says so in Recourse.assets; see Look and feel.

Routing a resource

Replace a call to resources with recourses. Everything resources takes, recourses takes too: only:, except:, a block of nested resources.

# config/routes.rb
- resources :posts, only: %i[index show] do
+ recourses :posts, only: %i[index show] do
-   resources :comments, except: :destroy
+   recourses :comments, except: :destroy
  end

The line draws what resources draws, and then supplies whatever the host lacks: a PostsController where none is defined, and a template for every action that controller serves. A controller the app already defines is left alone — the gem only fills the gap — and so is any template the app has under app/views/posts/.

The name has to be a model. recourses :posts with no Post class raises while the routes draw, naming the routes line, rather than failing later from somewhere inside a view.

What each action earns

Each of the seven actions is a screen, drawn by reading the model: its validators, its associations, its column types and its indexes.

RoutedEarns
indexA sidebar entry, a keyboard shortcut, and a paginated, searchable, sortable, filterable table. See Tables.
showA record’s page, every value drawn as what it is, encrypted ones masked until asked for. See Records and forms.
new, editA form with a field for each column’s kind, carrying what the validators say. A rejected write redraws it with the errors beside the fields.
create, updateThe write, a toast naming the record and leading to its page, and the row it landed on marked in the table.
destroyA button on the record’s own page, or on each row where no edit page would carry it, with a dialog naming what goes with the record before it goes.

A resource with an index and nothing else is a read-only table; one with create and no new gets a one-click Create button in the Add link’s place, on the host’s word that a bare record can stand. Nested resources default to only: %i[index new create]: the parent’s rows, and a form to add one. See Routes for every shape a routes line can take.

The sidebar and the shortcuts

Every resource routed index is an entry in the sidebar, in the order config/routes.rb declares them, never sorted. A resource without an index gets no entry rather than a broken one. Each entry carries the model’s icon, chosen by the model’s own name through the unicon gem, and a model may name another concept with recourse_icon.

Every entry answers to a letter of its own title, held with Option: Posts to P, and Pages, declared after it, to A, since P was taken. Holding Option underlines the letter in place, so the hint points at a key rather than at a number nobody can guess.

The foot of the sidebar holds the reader’s own controls: a moon or a sun that moves the page through the palettes and between light and dark, and — where the host drew a route named exit — the way out.

Securing the controllers

Every controller the gem defines inherits RecoursesController. The host defines that class itself, which is how a guard goes above every screen at once:

# app/controllers/recourses_controller.rb
class RecoursesController < Recourse::BaseController
  before_action :authenticate!
end

The behavior is in Recourse::BaseController, so a host redefining RecoursesController loses none of it. A controller the host writes for one resource — class PostsController < RecoursesController — inherits the same guard, and a bare action the host answers itself is a RecoursesController too, that being where an admin keeps the filters guarding it.
