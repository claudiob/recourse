Customizing

The gem only fills the gap: anything it draws, the host can write itself, and a file the host has is left alone. This guide is what to write for each kind of change, from one partial to a whole controller, and what stays the gem’s whatever the host writes.

A row of your own

A host changes one table by writing app/views/<resources>/_row.html.erb, one column call per cell with the content in a block. The record arrives under its own name, and the partial is rendered once for the header row with that local nil, so nothing outside a column block may assume it is present:

<%# app/views/posts/_row.html.erb %>
<%# locals: (post:) -%>

<%= column header: sort_header(:title) do %>
  <%= search_highlight post.title, :title %>
<% end %>

<%= column header: 'Author' do %>
  <%= post.author.name %>
<% end %>

Three helpers are public for this. column draws the cell, and takes anything tag does. sort_header draws a heading that sorts, and only where the column can be sorted. search_highlight marks what the search matched, and only in a column the search looked through — including the label of a record the search reached through a key, so a row drawn out of the author a post points at marks the name. The action columns and the bookmark square are the table’s rather than the row’s, and are still drawn ahead of whatever the partial defines.

A link in a cell leaves the table’s frame through turbo_link_to, never link_to, or Turbo replaces the table with Content missing rather than going there.

The fields of a form

A _fields.html.erb under the resource replaces the fields and keeps the form, the submit and the errors. Both new and edit render it, so a host writes one and never a second. The field helper the gem’s own partial uses is the gem’s, not a host’s: a host’s fields are ordinary form builder calls on the record the form already holds.

A template of your own

A show, edit or nested index template under the resource replaces the body of that page and nothing else. The card, its tabs, the buttons beside the breadcrumb, the delete and the tab’s title are the layout’s, drawn around whatever template answers, so a host’s page is its content alone. A page that wants the width to itself assigns @recourse_card = false; a page that wants another title sets content_for :title, which still wins.

A host template reads the record under the name a hand-written controller would set: @post for posts, @recourse_parent for the record a nested page stands under.

A scope behind a table

A controller of the host’s own is a RecoursesController, and one private method puts a scope behind a table the gem otherwise draws whole. The search, the sort, the filters, the pages and the cache all still come from the gem:

class Projects::CommentsController < RecoursesController
private

  def recourse_relation
    project = Project.find params.expect(:project_id)
    Comment.where task: project.tasks
  end
end

By default the relation is every row of the model, narrowed by the foreign key a nested route names. A relation may carry values of its own beside the columns — a select with an aggregate — and a _row partial reads them off the record.

A model behind a page

The route’s own name answers which model a page is about, by asking the app for a class of that name. A page named for something else — recourses :purchases listing a table of orders — names its model instead, with def recourse_model = Order. Private, like the relation: naming a model adds no action.

A record the parent does not name

A singular resource is read off the parent under the route’s name, whether by a has_one or a belongs_to. Where the parent has no association of that name the record is the host’s to find, and an override still wins where the gem could have resolved it:

class Projects::ManagersController < RecoursesController
private

  def find_resource
    assign @recourse_parent.team.manager
  end
end

assign sets both @recourse and the record’s own name. A find that answers nothing draws a page saying so, or the form where new is routed.

The writes

create, update and destroy are ordinary actions on Recourse::BaseController, and a host with something of its own to do on a write writes the action. What the gem does inside them is private API rather than a shelf to reach for. A bare action’s controller and a retrieval controller are written whole; see Routes and Retrievable tables.

What stays the gem’s

  • The sidebar, the breadcrumb, the search form and where they sit, unless the host replaces the whole layout; see Look and feel.
  • The card around a record’s pages, its tabs and the buttons beside the breadcrumb, whatever template answers.
  • The action columns and the bookmark square on a table, whatever row partial draws the rest.
  • Which columns a form permits: the editable columns, less what recourse_hidden keeps back. A host that hides a column the database requires has a form that cannot save; see Models.
