Positionable tables

A table whose model keeps an integer position is one a reader puts in order by hand. This guide is what the column earns, what the routes have to say, what keeps the numbers running, and how a host lists the same rows in a second order.

The column and the keyword

The column is the whole of the declaration: a model keeping an integer position has said its rows are in an order. The type is load-bearing, asked through type_for_attribute — a position holding a job title is a word about the row, not a place among rows, and a table of those is left alone. A column named otherwise is named in the model: def recourse_position = :ordering.

The routes say where a drop is reported, since a page nobody drags needs no route:

recourses :steps, positionable: true

That draws PATCH /steps/5/position under the index. A table is put in order from its index and from nowhere else, so the keyword is refused on a resource that draws none.

What the page does

A grip opens each row, dragging it moves the row, and the place it lands in is written to that route. The table is ordered by the column, whatever recourse_order would otherwise say: the order a table is read in and the order somebody put it in are one fact. The column itself is never drawn, since the row's place in the table already says it, and the form never asks for it.

The search box and the sorted headings stand down while the grips are drawn, and a q typed by hand is refused for the same reason: a filter shortens the page, and a drop on a shortened page would report a place among the rows that are left.

Whether a page is positioned is asked per page, not per model. A position means something under the parent it is counted within, so a flat model's own index is positioned and a listing nested under a parent is, while a listing of every row across every parent — where the positions run 1, 2, 3, 1, 2, 3 side by side — is not, and sorts and searches like any other.

What keeps the numbers running

What a drop reports is a row's place on the page, which is a position only while the numbers run 1, 2, 3 with no holes in them. So two things follow the column rather than the routes: a new row lands last among its own, and the gap closes behind one that goes, whether it was made behind a form or in a console. Both are callbacks every model carries and only a positioned one runs.

A model pointing two ways

The rows a position is counted among are those under the same parent, or the whole table where the model points nowhere. A model with one belongs_to needs no answer. One pointing two ways is asked rather than guessed, since numbering a step among every step there is would be the wrong answer given quietly, at the first write:

class Step < ApplicationRecord
  belongs_to :team
  belongs_to :person

  def recourse_siblings = team.steps
end

Without it, the first save raises naming the model and the method.

Opting out

A host that keeps the order itself writes def recourse_position = nil, which takes the grips off the table and both callbacks off the model together.

A second listing

A host with a second listing of a positioned model — a step's place among its team's steps, and another among the steps of whoever is to do them — names the second column on its controllers instead, and owns the write as well as the page. Both halves are told the same thing, since a drop on that listing would otherwise write the model's own column from a page showing the other:

module Ranking
  extend ActiveSupport::Concern

private

  def recourse_position = 'ranking'
end

class People::StepsController < RecoursesController
  include Ranking
end

class People::Steps::PositionsController < Recourse::PositionsController
  include Ranking
end

Recourse::PositionsController is public to subclass, and Recourse::Positioning is public for exactly that case: Recourse::Positioning.new(relation, column).close is what such a host calls to keep its own column contiguous when a row goes.
