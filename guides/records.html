Records and forms

A record has two pages, a look and a change, and they are the same page with the form taken out. This guide is how a value reads on the first, which field it gets on the second, the card both sit in, and what a write and a delete leave behind.

The card

A record’s pages are drawn in a card whose header holds one tab per page the record has: a look, a change, and then one per resource nested under it, in the order the routes nested them. A nested index’s tab reads 8 comments where the record keeps a counter and the bare Comments where it does not; a singular resource’s tab reads its model’s word in the singular. Tabs are links, each a page of its own with its own address and breadcrumb.

A nested page sits in the parent’s card, with its own tab current and the parent’s Show and Edit beside it. A form for a record that is not there yet gets no card, there being no other page of it to offer.

The card is the layout’s, not the template’s: it is drawn around whatever template answers, so a host writing its own show, edit or nested index writes its body and nothing else. The tabs, the buttons beside the breadcrumb, the delete and the tab’s title all stay. A page that wants the width to itself assigns @recourse_card = false.

The record’s page

One heading and one value per editable column — the same list the form offers, encrypted columns included — two to a row on a large viewport, and then Created and Updated at the end, always, whatever the table shows. Each value reads as what it is of: a foreign key as the label of what it points at, a date as Aug 12, 2026, an integer delimited, money with the currency, a percentage with its %, a phone punctuated, a boolean as Yes or No, an enum as a badge in the word the column holds. A value the record has nothing for reads as a dash, so a heading is never left over a gap.

A JSON payload gets a block of its own, pretty-printed, bounded and scrolling. A list opens behind a summary reading how many — 3 items — so a column of values does not push the page down until asked. A single attached file is the picture Active Storage makes of it, or its name, inside a link opening the whole file in a new tab. A counter is not on the page at all: the table is where a count belongs.

Masked values

An encrypted value arrives masked, one asterisk per character, with a Show beside it that swaps the plaintext in and then removes itself. What a screenshot catches is asterisks, and reading one value is a deliberate click. The form is the other way round: an encrypted attribute’s field carries the value in the clear, in the field its kind earns, since a value nobody can read is a value nobody can change.

The form

new and edit render the same form, titled New post or after the record’s label, with one field per editable column and then one per attachment. Which field a column gets follows its kind: a checkbox for a boolean, a menu for an enum, a number field stepped by what the column keeps — step="1" for an integer, the scale for a decimal — a date field, a datetime-local, a telephone field for a phone, an email input for an email, a textarea of one row for text, and a textarea one value to a line for a list. Money and a percentage are adorned with their unit rather than labelled twice. A column the database generates is never offered, since it would refuse whatever was typed.

Fields sit two to a row on a large viewport and stack below it. The submit is a solid primary button. A _fields.html.erb of the host’s own replaces the fields and keeps the rest; see Customizing.

What the validators say

What a value may be is the model’s business, so the browser is told what the validators say and never what the schema does. A length validator becomes maxlength and minlength; a format validator becomes pattern, with a title showing the shape it wants, read off the pattern — \d{5} reads Please match the format 00000; a numericality validator or a digits-only pattern becomes a numeric keyboard. A required attribute is a required field, and a belongs_to counts as required through its association.

An optional field says Optional in its placeholder. A required one shows the shape it expects instead where there is one — michael@example.com for an email — and nothing otherwise.

Comboboxes and typed references

A foreign key is a combobox listing every record of the other model by its label, with a search box, and Select… until a reader chooses. Two things turn it into a field to type into instead: the other model’s label has a length validator, so it is short enough to type; or the other table is too long to list, which is 200 rows. A typed reference is labelled Country code, takes the shape of that attribute from the other model, and is looked up on the way in — a value naming no record leaves the key nil and Must exist beside the field, which keeps what was typed. That is what keeps /orders/new from being a menu of every customer.

Errors and notes

A rejected write redraws the same page with the fields keeping what was typed. The control that failed is marked and the reason follows it, sentence-cased and bare — Must exist, Can't be blank — since the label above it already names the attribute. The message over the page is Post could not be created.

Under a field, where the database has said what its column is for, a line saying so; under a file field on an edit form, a line saying what the record is holding now — 2 files attached (a.png and b.png). The column comment is read off the schema, or off recourse_comment on an adapter that keeps none; see Models.

What a write leaves

A write that landed goes back to the index — or to the record’s own page where the routes drew no index, or to the parent’s page where they drew neither — with a toast naming the record by its label and leading to its page: Ada was created., the name a link where show is routed. The row it landed on is tinted in the table for as long as the toast stands. A delete names the model instead: Comment was deleted.

A rejected write with no form to send it back to — a bare action, a one-click Create — goes back to the page the button stood on, with what turned the write down as the message.

The delete

The Delete button stands beside the breadcrumb on the record’s own page, whichever of the two is open, and only where destroy is routed. It asks first, in a dialog naming the record and counting one level of what goes with it — :destroy children as deleted with it, :nullify ones as kept without it — and ending This cannot be undone.:

Delete Acme?

12 projects and 3 invoices will be deleted with it.
40 comments will be kept, without its account.
Anything under those goes too.

This cannot be undone.

Counted one level down and no further, one COUNT per has_many: counting the whole tree under an account would join every row it reaches to draw a page. A row a model will not give up — a before_destroy that throws :abort — stays, and the page says Category could not be deleted. rather than raising. A model may word its own button and heading, Disconnect rather than Delete; see Models.
